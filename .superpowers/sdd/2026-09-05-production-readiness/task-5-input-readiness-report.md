## Pinned native keyboard route: source findings, not a runtime diagnosis

The installed [CEF version header](/Users/dvle/Library/Caches/tauri-cef/151.3.24/cef_macos_aarch64/include/cef_version.h:38) identifies CEF 151.3.24, commit `2384915b7b1f0fe5ad1107e48d80c34e86b698d7`, Chromium 151.0.7922.174. The links below pin upstream implementation to that commit.

1. Dive's vendored [keyboard handler](/Users/dvle/.codex/worktrees/dive-production/dive-browser/vendor/tauri-runtime-cef/src/cef_impl/client/keyboard.rs:20) overrides only `on_pre_key_event`. It blocks the specified developer-tools shortcuts when developer tools are disabled; Cmd+T otherwise returns zero without setting `is_keyboard_shortcut`. There is no `on_key_event` override. The pinned Rust binding's [default implementation](/Users/dvle/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/cef-151.8.1+151.3.24/src/bindings/aarch64_apple_darwin.rs:20468) returns zero.
2. CEF's [keyboard contract](/Users/dvle/Library/Caches/tauri-cef/151.3.24/cef_macos_aarch64/include/cef_keyboard_handler.h:45) runs these callbacks on its UI thread. `OnPreKeyEvent` precedes renderer delivery; `OnKeyEvent` follows the renderer/page JavaScript's opportunity to handle the event. [BrowserContentsDelegate](https://github.com/chromiumembedded/cef/blob/2384915b7b1f0fe5ad1107e48d80c34e86b698d7/libcef/browser/browser_contents_delegate.cc#L242) translates the pre-handler return/shortcut flag into the Chromium result and calls the post-handler for eligible unhandled events.
3. [AlloyBrowserHostImpl::HandleKeyboardEvent](https://github.com/chromiumembedded/cef/blob/2384915b7b1f0fe5ad1107e48d80c34e86b698d7/libcef/browser/alloy/alloy_browser_host_impl.cc#L912) skips `skip_if_unhandled` events, then tries the client handler, then the platform delegate. The [native macOS delegate](https://github.com/chromiumembedded/cef/blob/2384915b7b1f0fe5ad1107e48d80c34e86b698d7/libcef/browser/native/browser_platform_delegate_native_mac.mm#L415) calls the main menu's `performKeyEquivalent:` for native key-down events. Thus this explicit CEF menu route is an unhandled-event fallback after page processing. This does not establish that AppKit has no other earlier key-equivalent route, or that run8 used this particular fallback.
4. The pinned [Tauri menu callback](/Users/dvle/.cargo/git/checkouts/tauri-69fbbe4d0942e697/7132030/crates/tauri/src/app.rs:2542) sends `EventLoopMessage::MenuEvent` through the runtime proxy. [RuntimeContext::send_message](/Users/dvle/.codex/worktrees/dive-production/dive-browser/vendor/tauri-runtime-cef/src/runtime.rs:253) handles messages immediately when already inside its main-thread dispatch; otherwise it enqueues and wakes the loop. An unconditional extra queue hop cannot be inferred from `send_event` alone.
5. Once [Dive's menu listener](/Users/dvle/.codex/worktrees/dive-production/dive-browser/apps/desktop/src-tauri/src/menu.rs:246) runs, it focuses the relevant chrome before emitting the frontend command. [Window-aware focus selection](/Users/dvle/.codex/worktrees/dive-production/dive-browser/apps/desktop/src-tauri/src/engine.rs:853) preserves popout targeting. Inside runtime dispatch, [SetFocus handling](/Users/dvle/.codex/worktrees/dive-production/dive-browser/vendor/tauri-runtime-cef/src/webview.rs:690) calls CEF directly. [CEF SetFocus](https://github.com/chromiumembedded/cef/blob/2384915b7b1f0fe5ad1107e48d80c34e86b698d7/libcef/browser/browser_host_base.cc#L443) posts only when off its UI thread; the [macOS implementation](https://github.com/chromiumembedded/cef/blob/2384915b7b1f0fe5ad1107e48d80c34e86b698d7/libcef/browser/native/browser_platform_delegate_native_mac.mm#L380) sets the content view as first responder. There is no source basis here for adding another focus dispatch.

The earliest available CEF interception is `OnPreKeyEvent`, but moving native-menu dispatch there for every modifier chord would change page shortcut precedence. Even an exact Cmd+T-only early interception changes behavior for a page that currently consumes Cmd+T. Preserving that precedence strictly means keeping the renderer opportunity and using the later callback/fallback. A future browser-owned accelerator policy could narrowly intercept only an enabled, exact native launcher equivalent on macOS, retaining nonmatching events, developer-tools policy, keyboard-layout matching and popout targeting; this is a candidate requiring a documented browser-shortcut precedence policy and qualification, not an implemented fix. The approved browser-polish scope permits resolving that routine design choice without another user approval.

The next discriminating diagnostic is gated, passive monotonic receipts at pre-key and post-key callback entry/return, native menu action receipt, runtime immediate-versus-enqueued delivery, app menu listener entry, and chrome focus call completion/first-responder identity. Correlate a fixed launcher classification or native event sequence/timestamp with browser/view IDs and the existing chrome trace; do not record arbitrary key characters, page values or clipboard data. Keep callback returns and shortcut flags unchanged. This separates time before native-menu recognition, time awaiting runtime dispatch, and focus application from the already measured DOM mount/focus interval. Until those receipts exist, the warm leading-character loss is confirmed but its exact native boundary remains open. No production code, build or native launch was performed for this source mapping.
