# Task 7 — bounded response capture

Status: implementation, focused regressions and exact-binary native capture matrices pass. Overall performance task remains OPEN, including measured same-site renderer RSS retention.

Before: every finished response whose MIME contained `json` spawned an independent full `Network.getResponseBody` request. Truncating after allocation did not bound native/IPC allocations; retained bodies could approach64MiB per tab. Slim network listings cloned the full body/header records before discarding those fields.

Now: every Network.enable call uses explicit2MiB total/64KiB resource limits. More importantly, response admission requires a fully observed non-lagged sequence of native decoded Network.dataReceived bytes at or below64KiB; wire bytes and Content-Length cannot admit compressed oversized responses. Unknown sizes are omitted with explicit reasons. Each tab has one worker and16 queued jobs, with4 body calls across all tabs. Closure aborts queued/in-flight capture, and both metadata and body writes are guarded by the original native view generation under the host lock. Complete UTF-8/base64 bodies are retained only within64KiB; each tab evicts oldest bodies above2MiB without dropping metadata. MCP/HAR distinguish omitted bodies from empty payloads. Slim listing construction no longer clones bodies/headers.

Primary source: pinned Chromium151.0.7922.174 inspector_network_agent.cc demonstrates Network.enable resets omitted limits, and getResponseBody can bypass inspector resource limits through Blob/CachedResource fallbacks. Native limits alone are not an admission proof:
