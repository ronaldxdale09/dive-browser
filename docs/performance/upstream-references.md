# Upstream performance references

These sources guide hypotheses, not DIVE performance claims. Benchmark exact builds before adopting a change. No upstream implementation has been copied into DIVE in this pass; any future reuse must preserve its license and attribution.

Reviewed 2026-09-06. Some explanatory articles are historical; current engine behavior must be checked against DIVE's pinned Chromium/V8 source before relying on a flag or API. Moving main-branch sources are architectural references, not version-matched numerical comparisons.

The existing `shlex` 2.0.1 dependency now parses quoted diagnostic Chromium arguments without executing a shell. This fixes multi-option V8 profiling values; it is not itself a RAM optimization.

CEF sandbox follow-up: [upstream helper initialization](https://github.com/chromiumembedded/cef/blob/master/tests/cefsimple/process_helper_mac.cc) initializes the macOS sandbox before loading CEF. DIVE's pinned Tauri workspace disables runtime default features; native process inspection confirmed `--no-sandbox`. Earlier performance report wording incorrectly claimed it was enabled and has been corrected. Sandbox qualification remains separate from IPC/origin permission tests.

Release check: crates.io API on 2026-09-06 reports `cef` 151.8.1+151.3.24 as latest stable (published 2026-09-03). The packaged framework reports 151.3.24.0 and installed headers identify Chromium 151.0.7922.174, consistent with the pinned crate. No newer stable Rust binding was found; a blind version bump is not a demonstrated optimization.

Sandbox fix: DIVE now explicitly enables the pinned runtime's `sandbox` feature. The native verifier uses the [Chromium Seatbelt query](https://chromium.googlesource.com/chromium/src/+/refs/tags/140.0.7263.0/sandbox/mac/seatbelt.cc); before/after queries on both owned renderers returned false/true respectively. Full native checks qualify functionality independently.

Allocator follow-up: source for pinned Chromium 151.0.7922.174 shows `PartitionAllocAdjustSizeWhenInForeground` enabled on macOS, with foreground empty-slot retention up to the compiled maximum (1024 slots when the large-ring build option is active), compared with a 128-slot background ring. `PartitionAllocLargeEmptySlotSpanRing` starts at 128. The allocator's initial periodic reclaim delay is one minute. This suggests a bounded foreground cache-size experiment, not proof that smaller caches improve overall performance. Sources: [feature defaults](https://chromium.googlesource.com/chromium/src/+/refs/tags/151.0.7922.174/base/allocator/partition_alloc_features.cc), [allocator policy](https://chromium.googlesource.com/chromium/src/+/refs/tags/151.0.7922.174/base/allocator/partition_alloc_support.cc). No allocator setting changed yet.

2026-09-07 navigation follow-up: [version-pinned CEF resource request pipeline](https://github.com/chromiumembedded/cef/blob/2384915b7b1f0fe5ad1107e48d80c34e86b698d7/libcef/browser/net_service/resource_request_handler_wrapper.cc) confirms that an attached resource handler enters extra cookie/interception work. A bridge-endpoint-only handler pilot reduced pre-request delay from roughly 14 ms to 0.5 ms, but the delay moved to page commit and total reload did not improve. Patch removed; no resulting production performance claim. A native about-to-wait drain also showed no end-to-end benefit and was removed.

Browser-wide traces then exposed repeated OS device-permission refresh tasks on the browser thread. [Chromium 151 permission context](https://chromium.googlesource.com/chromium/src/+/refs/tags/151.0.7922.174/components/permissions/permission_context_base.cc) posts non-granted refreshes asynchronously; [Chromium 152](https://chromium.googlesource.com/chromium/src/+/refs/tags/152.0.7977.82/components/permissions/permission_context_base.cc) refreshes directly. Scheduling changes can move work relative to a page load event, so the harness now retains a visible double-rAF milestone too. No permission checks are removed.

[CEF API versioning](https://github.com/chromiumembedded/cef/blob/master/docs/api_versioning.md) allows stable-API clients to use a later framework that still supports that API and matches its hash; it explicitly does not guarantee behavior across Chromium versions. Local headers select stable API 15101, and both pinned runtime and helper call api_hash with that version. This supports researching an isolated framework-upgrade experiment, subject to archive verification, API hash compatibility and full native checks; it does not yet establish a compatible or faster newer build.

Allocator evaluation: [Rust global allocator documentation](https://doc.rust-lang.org/std/alloc/index.html) and [Microsoft mimalloc](https://github.com/microsoft/mimalloc) describe a Rust allocation strategy, not a replacement for Chromium's independent managed/native heaps. Read-only CEF 152 diagnostics show only about 4.4 MiB allocated in the parent process's malloc zones; no evidence yet supports a material whole-browser gain from this extra dependency, so none was added.
