# Browser performance goal

Latest verified results and current limitations: [RESULTS.md](RESULTS.md). The investigation below retains historical experiments and intermediate status.

## Acceptance

Outperform both Chrome and Brave in matched whole-browser physical footprint with one and ten tabs, local document load, launch to document ready, and complete installed application size. Preserve developer tools, permissions, privacy, media, containers, navigation, and process isolation. Do not substitute RSS for physical footprint, disable features for the comparison, or advertise a universal speedup from one synthetic page.

Worktree: `dale/performance-goal`, based on `ec39bb275b735bf442fdef002f6be70d025c3969` (0.1.13). Changes remain uncommitted and unpublished.

## Investigation and validation

1. Build an unchanged source control bundle separately, preserving the installed app and main checkout.
2. Attribute physical footprint by process and UI/page heap. Diagnose feed overhead separately; diagnostic feature toggles are never accepted as production benchmark wins.
3. Stop pausing document requests when privacy is the only interception consumer: the privacy matcher already allows documents. Enabled workspace rules must retain document interception. Validate tracker blocking, redirects, custom document rules and media.
4. Exclude unused production UI source maps from the installed app; keep an opt-in diagnostic build. Measure actual compressed embedded-binary savings, not just raw map sizes.
5. Investigate independent tab bootstrap operations and unnecessary UI startup allocations. Preserve the barrier that installs all security and activity instrumentation before navigation.
6. Run `pnpm check`, exact-binary native checks, and fresh before/after measurements. Broaden to multi-origin workloads and normal browsing before claiming the goal achieved.

### Startup geometry finding

The promoted harness recorded `startupFixture.viewport: [1,1]` for the first candidate. `TabHost::new` initialized its page bounds to 1×1 until the React layout report arrived. Consequently, earlier launch numbers measured a load callback, not a usable visible page. They remain raw evidence but are not valid claims about user-visible startup readiness.

A follow-up initializes content bounds from the actual logical window size and saved rail preference, using the same 84-pixel chrome and 960-pixel rail-collapse threshold as the frontend. React retains ownership of subsequent panel/split geometry. The benchmark now waits for document load, a visible viewport of at least 400×300, and two animation frames, then timestamps the host callback. It records both the viewport at load and the ready viewport. This new startup definition requires fresh runs for every browser; earlier launch numbers must not be pooled with it.

### Native tool/eviction regression found during qualification

The first geometry native run failed after a discarded tab was recreated: `page_wait_for` returned CDP `Inspected target navigated or closed` during document replacement. Native qualification already had narrow handling for this readiness race, but the production MCP wait did not. Production waits now retry only three known navigation-readiness error strings while the session is live and the existing deadline remains in force; closed sessions, transport failures, script errors and invalid locators fail normally.

Separately, tool calls acquired a CDP session without holding the existing activity-pending guard for their whole operation. `ToolSession` now acquires that guard while holding the host lock (the same lock as native discard admission), retaining it through polling/awaits and releasing it on completion or cancellation. Three regression tests cover concurrent operations, cancellation and narrow retry classification.

The live script now verifies startup page A while it is active, observes its persisted discard state read-only (without accidentally waking it), and explicitly activates it before checking restoration. Added an actual long-running MCP evaluation: after the page signals that the call started, move it to the background, prove it remains active while the tool is running, then require discard after the tool completes and successful wake afterward. The pre-fix geometry binary failed this regression with `session closed` and a contemporaneous discard receipt (`tool-protection-before.log`); this diagnostic omitted YouTube and ran during compilation, so its timings are not performance evidence.

The guarded follow-up binary is `target/performance-goal/guarded/Dive.app`, SHA-256 `5ce9ac653edc44573ccdbe87ab565f0f9cf26ea77d3ba92e6094c6b2025e12ae`. Full `pnpm check` and packaging succeeded; its native qualification and fresh matrix remain in progress.

The guarded binary passed the full native check, including the new in-flight-tool/background-discard regression, YouTube playback, all other browser checks, isolated renderer crash and four native lifecycle cycles. CDP n=100: p50 0.159 ms, p95 0.277 ms, max 0.634 ms. Evidence: `guarded-live.log`, `guarded-fetch.log`, `target/lifecycle-probes-1788702831368816000`. Complete bundle size: 370,926,713 bytes. The corrected harness verifies the new initial geometry: the first guarded run loaded and became ready at 1072×736, rather than 1×1. It also inventories targets after one-tab memory sampling.
